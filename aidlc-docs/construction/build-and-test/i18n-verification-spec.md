# i18n 검증 체계 명세 (Dev-B 구현 대상)

> **목적**: 번역 결과를 4계층으로 검증하고, 계층별로 **책임자에게 라우팅**한다.
> **작성**: Dev-A → Dev-B 전달
> **관련**: US-2.1(품질 검증), US-2.2(용어 발견), US-2.4(피드백 루프)

---

## 핵심 원칙

검증에서 발견되는 문제는 **고칠 사람이 다르다**. 이를 구분하지 않으면
Dev-B가 번역 수정으로 해결하려 하다가 근본 원인을 놓친다.

| 계층 | 검출 대상 | 고칠 사람 |
|------|-----------|-----------|
| Layer 1 | 구조적 결함 | Dev-A (재번역) |
| Layer 2 | 용어집 위반 | Dev-A (재번역) / Dev-B (용어집 등록) |
| Layer 3 | 문맥 오역 | Dev-B (용어집 등록) → Dev-A (재번역) |
| Layer 4 | **번역 대상이 아닌 텍스트** | **Dev-A (추출 필터 수정)** |
| 부가 | 원문 오타/구조 문제 | 디자이너 / UX 담당 |

Layer 4는 번역을 고쳐선 안 된다. 애초에 추출되면 안 됐던 항목이므로 Dev-A에게 반송한다.

---

## 입력

| 파일 | 생성자 | 용도 |
|------|--------|------|
| `src/locales/{en,ko,ja,zh-CN}.json` | Dev-A | 검증 대상 |
| `src/components-map.json` | Dev-A | role/프레임 문맥 참조 |
| `requirements/domain-glossary.md` | Dev-B | 용어집 기준 |
| `glossary-proposal.md` | Dev-A | 용어 등록 후보 |

---

## Layer 1 — 기계적 검증

locale JSON만으로 판정 가능. 코드로 100% 자동화.

| 규칙 ID | 검사 | 판정 |
|---------|------|------|
| L1-01 | 4개 언어 key 구조 완전 일치 | 불일치 시 FAIL |
| L1-02 | 값이 빈 문자열이 아님 | 빈 값 FAIL |
| L1-03 | ko/ja/zh 값이 en과 동일하지 않음 (미번역 탐지) | 고유명사 예외 목록 필요 |
| L1-04 | placeholder(`{0}`, `{{name}}`) 개수·이름이 en과 일치 | 불일치 FAIL |
| L1-05 | 앞뒤 공백 없음 (`v === v.trim()`) | 공백 FAIL |
| L1-06 | 번역 길이가 en의 2배 이내 (UI 깨짐 방지) | 초과 WARN |

**L1-03 주의**: `LG Electronics`, `SSO`, `API` 처럼 번역하지 않는 게 정답인 항목이 있다.
고유명사 화이트리스트를 두고 예외 처리할 것.

---

## Layer 2 — 용어집 준수

### L2-01: 복합어 내부까지 검사 (중요)

단독 단어만 비교하면 놓친다. **부분 문자열까지 검사해야 한다.**

```
용어집: Workspace → 워크스페이스

en "Workspace/Group Settings" 의 ko 에 "워크스페이스" 포함 여부 검사
  → "작업 공간/그룹 설정"  이면 FAIL
  → "워크스페이스/그룹 설정" 이면 PASS
```

### L2-02: 같은 영어 → 다른 한국어 (일관성 위반)

동일 영어 텍스트가 서로 다르게 번역된 경우.

### L2-03: 다른 영어 → 같은 한국어 (구분 소실)

서로 다른 원문이 같은 번역으로 합쳐지면 의미 구분이 사라진다.

> 실제 발견: `Settings` 와 `Setting` 이 둘 다 "설정"

### L2-04: 용어집 미등록 반복 용어

2회 이상 등장하지만 용어집에 없는 용어 → 등록 제안.
Dev-A가 `glossary-proposal.md`로 이미 제공하므로 이를 검토 대상으로 삼는다.

**주의**: `requirements/domain-glossary.md` 하단의 "용어 추가 요청 형식" 예시 행이
파서에 실제 용어(`NewTerm`)로 읽힌다. 템플릿 행을 주석 처리하거나 별도 섹션으로 분리 필요.

---

## Layer 3 — 문맥 적합성 (EXAONE 역검증)

프로젝트의 핵심 가치가 걸린 계층. **단건으로 물으면 못 잡는다.**

### 검증 방법

EXAONE에 아래를 함께 제공하고 판정을 요청한다:

1. 원문 + 번역
2. **같은 프레임의 주변 텍스트 목록** (`components-map.json`에서 추출)
3. 도메인 정보

### 왜 주변 문맥이 필수인가 — 실제 사례

```
en: Vertical Type *
ko: 세로 유형          ← 오역
```

같은 프레임의 주변 필드: `System Integrator`, `Business Type`, `End Customer`

→ B2B 파트너 분류 화면이므로 `Vertical`은 화면 방향이 아니라
  **산업 분야(vertical market)**. "산업 분야" 또는 "버티컬"이 맞다.

단독으로 "Vertical Type을 번역하라"고 하면 "세로 유형"이 나온다.
주변 필드를 함께 줘야 잡힌다.

이는 `Player → 재생 장치` 와 동일한 유형이며, 용어집에 없어서 통과했다.

### 출력

문맥 위반 발견 시 → 용어집 등록 제안 → Dev-A 재번역 요청

---

## Layer 4 — 번역 대상 적격성 → Dev-A 반송

번역 품질 문제가 아니라 **추출 단계 결함**이다. Dev-B는 검출만 하고 반송한다.

### 검출 유형

| 유형 | 판별 힌트 |
|------|-----------|
| 샘플 주소 | 도로명/지번 패턴, `bldg`, `-ro`, `-gu` |
| 샘플 파일명 | `.jpg`, `.png`, `FileName`, `sample` |
| 더미 텍스트 | `supporting text`, `Label`, `Button`, 같은 단어 반복 |
| 샘플 데이터 | `Business A`, `Workspace A1`, `Device N` 등 알파벳/N 접미사 |
| 코드·ID 값 | 대문자 약어, 버전 문자열 |

### 판별이 애매한 경우

`components-map.json`의 `type`(role)과 프레임 위치를 함께 본다.
디자인 시안의 예시값은 보통 입력 필드 내부나 테이블 셀에 위치한다.

---

## 부가 — 원문 문제 (디자이너 피드백)

번역으로 해결 불가. UX 담당에게 전달할 항목.

| 유형 | 실제 발견 |
|------|-----------|
| 원문 오타 | `Thema 03`, `Thema 04` → `Theme` |
| 원문 오타 | `...set the detailes for...` → `details` |
| 문장 조각 | `is required` 단독 → 한국어 어순상 조립 불가 |

**문장 조각 문제**: 원문이 `{field} is required` 형태여야 한다.
영어는 조각을 이어붙일 수 있으나 한국어는 어순이 달라 불가능하다.
i18n 구조 문제이므로 디자인 단계에서 문장 단위를 지켜야 한다.

## 출력 산출물

Dev-B는 검증 실행 시 아래 2개를 생성한다.

### 1. `i18n-report.md` — 전체 검증 리포트

```markdown
# i18n 검증 리포트

실행 시각: <ISO timestamp>
대상: src/locales/*.json (<N> keys)

## 판정 요약
| 계층 | 규칙 | PASS | FAIL | WARN |
|------|------|------|------|------|
| L1   | 6    | ...  | ...  | ...  |
| L2   | 4    | ...  | ...  | ...  |
| L3   | -    | ...  | ...  | ...  |

## 종합 판정: PASS / FAIL

## 상세 (FAIL 항목)
| 규칙 | key | en | 현재 번역 | 문제 | 조치 대상 |
|------|-----|----|-----------|------|-----------|
```

### 2. `extraction-issues.md` — Dev-A 반송 문서

Layer 4 및 원문 문제를 Dev-A/디자이너가 바로 조치할 수 있는 형태로 정리한다.

```markdown
# 추출 이슈 반송 (Dev-B → Dev-A)

생성 시각: <ISO timestamp>
대상 locale: <N> keys 중 <M>건 반송

## A. 번역 대상 제외 요청 (추출 필터 수정)

| key | en 원문 | 유형 | 제외 사유 |
|-----|---------|------|-----------|
| ... | ...     | 샘플 주소 | 디자인 시안 예시값 |

→ Dev-A 조치: `isTranslatableUIText()` 필터 보강

## B. 원문 문제 (디자이너 전달)

| en 원문 | 문제 | 제안 |
|---------|------|------|
| Thema 03 | 오타 | Theme 03 |

→ 조치: UX 담당 전달

## C. 용어집 등록 요청 (Dev-B 승인 완료분)

| English | ko | ja | zh-CN | 근거 |
|---------|----|----|-------|------|
| Vertical | 산업 분야 | 業種 | 行业领域 | B2B 파트너 분류 문맥 |

→ Dev-A 조치: 용어집 반영 후 재번역
```

---

## 피드백 루프 (US-2.4)

```
Dev-A 번역
   ↓
Dev-B 검증 (Layer 1~4)
   ↓
 ┌─ PASS ────────────→ Dev-C 컴포넌트 생성
 │
 └─ FAIL
      ├─ Layer 1/2/3 → i18n-report.md      → Dev-A 재번역
      ├─ Layer 4     → extraction-issues.md → Dev-A 필터 수정
      └─ 원문 문제    → extraction-issues.md → 디자이너
```

재시도 상한: 3회. 초과 시 사람에게 에스컬레이션.

## 스크립트 배치

`package.json`에 이미 자리가 있다.

| 스크립트 | 담당 계층 |
|----------|-----------|
| `npm run validate:i18n` | Layer 1, 2, 4 (로컬 판정, API 불필요) |
| `npm run glossary:audit` | Layer 2 심화 + 용어 제안 |
| (신규 필요) | Layer 3 (EXAONE 호출 필요) |

Layer 1/2/4는 API 없이 동작해야 한다. CI에서 빠르게 돌릴 수 있어야 하고,
API 장애 시에도 기본 검증은 되어야 한다.

## 참고: 현재 알려진 결함 (Dev-A 자체 점검분)

Dev-B 검증 체계 구축 시 **테스트 케이스로 활용**할 것.
아래는 이미 존재가 확인된 항목이므로, 검증 체계가 이를 검출하지 못하면 규칙이 부족한 것이다.

| 계층 | 건수 | 예시 |
|------|------|------|
| Layer 2 (L2-03) | 1 | `Settings`/`Setting` 둘 다 "설정" |
| Layer 3 | 1 | `Vertical Type` → "세로 유형" (오역) |
| Layer 4 | 12 | 샘플 주소 2, 파일명 1, 더미 4, 샘플 데이터 5 |
| 원문 문제 | 4 | `Thema` 2, `detailes` 1, `is required` 1 |

Layer 1은 현재 위반 0건 (key 구조 일치 110개, 공백 0건, placeholder 보존).
